AWS Data Engineering Labs

Two AWS pipeline designs exploring batch analytics and real-time event processing, with different choices for ingestion, compute, queries and persistence.

Explore source and documentation ↗ ← Engineering Evidence

Engineering question

How should the design of a data pipeline change when the workload moves from periodic analytics to low-latency event processing? These labs compare the service boundaries and storage approaches of both models.

01 · Batch analytics architecture

Amazon S3 → AWS Glue → Amazon Athena

Object storage provides the landing zone, Glue supports transformation and catalogue-oriented processing, and Athena enables SQL-based analysis of data stored in S3.

  • Focus: scheduled or periodic processing of collected datasets.
  • Design consideration: data formats, transformation steps and query patterns matter more than immediate per-event responses.

02 · Real-time event architecture

Amazon Kinesis → AWS Lambda → Amazon DynamoDB

Kinesis provides event ingestion, Lambda handles event-driven processing, and DynamoDB stores results for low-latency access patterns.

  • Focus: responding to incoming events instead of waiting for a batch window.
  • Design consideration: throughput, retry behavior, event ordering and idempotency become important concerns.

Key architecture trade-offs

Batch: simpler scheduling and query-oriented storage for workloads that tolerate processing delay.

Streaming: lower processing latency, balanced against more demanding event-handling and operational design.

Neither is universally better; the choice depends on how quickly results are needed and how they are consumed.

What this project demonstrates

  • Comparing batch and streaming data architecture using managed AWS services.
  • Selecting services to match ingestion rate, processing latency and persistence needs.
  • Explaining architectural boundaries and the trade-offs behind them.
